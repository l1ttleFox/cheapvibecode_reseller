# MVP кабинета покупателей CheapVibeCode

Продажа и биллинг выполняются владельцем вручную. Покупатель получает готовый
API-ключ CheapVibeCode. Все запросы к моделям идут непосредственно в CheapVibeCode.

## MVP

1. Актуальный баланс по ключу через `/v1/balance`, без сессии владельца.
2. Инструкции интеграции из Docs CheapVibeCode, локальная версионированная копия
   команд установки с прямыми ссылками на установщики провайдера.
3. Каталог `/v1/models` как вспомогательные данные для выбора модели.

Backend предоставляет только GET `/api/account`, `/api/instructions`, `/api/models`.
Проксирование генераций, локальный биллинг, БД истории и воркер в MVP не входят.
Дизайн интерфейса отложен; существующий UI используется для баланса и инструкций.

## Инструкции

Источник: `/portal/docs` и JS bundle страницы, ссылка и дата снимка в ответе API.
Команды установщиков переносятся без запуска на сервере. Автосинхронизация пока
не заявляется; собственные SDK-примеры явно отделены от инструкций провайдера.
Проверка: правильная ОС, маршрут установщика, авторизация и прямой endpoint.

## История — исследование после MVP

Общий dashboard не даёт принадлежность запроса ключу. Возможный сборщик читает
JSON request-logs и отдельные счётчики ключей через сессию владельца.

- Сначала выяснить доступность `tokens_used` каждого ключа. По документации
  `/v1/balance` возвращает min(баланс аккаунта, остаток лимита), поэтому его дельта
  не всегда соответствует собственным расходам ключа.
- Сопоставлять суммы `cost_tokens` с дельтами за перекрывающиеся интервалы,
  учитывать задержку публикации, параллельность, изменение лимитов и пополнения.
- Общий баланс аккаунта не идентифицирует ключ. Совпадение суммы не является
  доказательством: возможны одинаковые стоимости и разные наборы запросов.
- Неразрешённые совпадения оставлять неопределёнными; нулевые списания без
  дополнительных сигналов ключу не приписывать.
- Если потребуется хранение только до закрытия вкладки, использовать память
  вкладки/sessionStorage. Это не устраняет необходимость состояния сборщика
  для сопоставления временных интервалов.

## Проверки

Баланс по разным ключам, нулевой остаток, ошибки upstream, прямые инструкции,
отсутствие генерационных маршрутов. Тесты не расходуют реальные ключи.
